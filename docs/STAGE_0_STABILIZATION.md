# JULI — Етап 0: технічна стабілізація перед Memory

*Підготовлено 03.11.2026 на основі аудиту репозиторію (`claude/JULI_Audit_2026-11-03.md` у проєкті «диплом + стаття»).*

Мета етапу: нижні шари (Tools → Collector → Monitoring → AgentCore → LLM) мають давати чесні, свіжі, компактні та однорідні дані, перш ніж ми почнемо будувати Memory. Memory не реалізується на цьому етапі.

## Завдання 1. Уніфікований ToolResult

**Проблема.** `get_system_state` повертає `success`, навіть коли вкладений інструмент упав. `cpu/memory/disk` при помилці повертають `data={}`, `pressure` — `data=None`. `list_processes` і `get_process_info` будують словник вручну.

**Зробити:**
- Усі інструменти в `app/tools/` повертають результат тільки через `make_tool_result`.
- При `status="error"` поле `data` дорівнює `None`.
- `get_system_state` агрегує статус:
  - усі три частини `success` → `success`;
  - частина впала → `partial`, у `data` для упалого ресурсу `None`, в `error` код `SYSTEM_STATE_PARTIAL` і повідомлення зі списком упалих ресурсів та їхніх кодів;
  - усі впали → `error`, `data=None`.
- `run_collector`: збій одного циклу (неуспішний стан або валідація) логуються і цикл продовжується, а не зупиняє весь Collector. `collect_system_snapshot` і далі записує snapshot тільки при повному `success`, без вигаданих значень.
- Перевір усіх, хто викликає ці інструменти (collector, dashboard, monitoring, тести).

**Тести:** success, partial, error для `get_system_state`; `data=None` при помилці кожного інструмента; Collector не падає в циклі при одному невдалому вимірюванні.

## Завдання 2. Конфігурація, запуск і версії схеми БД

**Проблема.** `initialize_database()` викликається тільки в тестах, і на чистій установці Collector падає з `no such table`. Шлях до БД відносний і продубльований у dashboard. `main.py` порожній. Немає механізму міграцій для майбутніх таблиць Memory.

**Зробити:**
- `app/config.py`: `PROJECT_ROOT` (від розташування файлу), `DB_PATH` = `JULI_DB_PATH` або `PROJECT_ROOT/data/juli.db`, `COLLECTOR_INTERVAL_SECONDS=10`, `RECENT_WINDOW_MINUTES=15`, `MONITORING_CONTEXT_MAX_CHARS=4000`; кожне значення можна змінити змінною оточення `JULI_*`.
- `app/core/database.py`:
  - `get_connection()` бере шлях із config;
  - `ensure_schema()` повторно викликати безпечно, вона має список міграцій і веде версію через `PRAGMA user_version`;
  - міграція 1 — наявна таблиця `system_snapshots` (`CREATE TABLE IF NOT EXISTS` з **тією самою** схемою, на наявній базі тільки виставляє `user_version=1`);
  - `initialize_database()` лишається як сумісний псевдонім.
- Порядок запуску: config → `ensure_schema()` → tools → monitoring/agent → UI.
- `main.py` (argparse):
  - `init-db` — створити або оновити схему, вивести версію;
  - `collect [--interval N]` — запустити Collector;
  - `analyze` — один цикл моніторингу і коротке текстове зведення.
- `app/dashboard.py`: шлях із config, `ensure_schema()` при старті, читати тільки останні N записів (наприклад 2000), а не всю таблицю.

**Перед запуском на реальній базі** поясни мені, що саме зміниться (очікується тільки `user_version`), і зроби резервну копію.

**Тести:** на порожньому тимчасовому каталозі (`JULI_DB_PATH`) `collect_system_snapshot` працює без ручної ініціалізації; `ensure_schema()` двічі поспіль нічого не ламає; наявні дані зберігаються; версія схеми правильна.

## Завдання 3. Current / Recent / Historical у моніторингу

**Проблема.** `run_monitoring_cycle()` аналізує останні 1000 snapshots без часового фільтра. На реальній базі аномалії CPU з експерименту 31.10 потрапляють до LLM як «поточні», хоча найновішому snapshot кілька діб. Поля свіжості даних немає.

**Зробити** (нові ключі поруч зі старими):
- параметри `recent_window_minutes` (з config) і `now` (для тестів, за замовчуванням поточний UTC);
- `freshness`: `latest_snapshot_timestamp`, `latest_snapshot_age_seconds`, `stale_after_seconds` (3 × інтервал), `state`: `fresh` | `stale` | `no_data`;
- `current`: значення CPU, RAM і Disk з найновішого snapshot плюс його timestamp; `None`, якщо даних немає;
- `recent`: `window_minutes`, threshold-аномалії, стійкі серії та significance assessments, які потрапляють у вікно;
- `historical`: тільки зведення, тобто кількість threshold-аномалій і серій поза вікном, timestamp останньої аномалії, перелік метрик;
- якщо `state != fresh` → `status: "partial"` і data issue `stale_data` (або `no_data`).

Значення не вигадуються: якщо даних немає, повертається `None` або `unknown`.

**Тести:** з фіксованим `now`: fresh, stale, no_data; аномалія у вікні потрапляє в recent, поза вікном — тільки в historical; старі ключі на місці.

**Перевірка на копії реальної бази:** очікується `stale`, 0 recent аномалій, 4 historical.

## Завдання 4. Context Builder

**Проблема.** `AgentCore` передає LLM повний JSON моніторингу: близько 23.6 тис. символів (≈6 тис. токенів) на кожне повідомлення. Приблизно 78 % займає PSI, бо кожен Evidence Profile містить повну копію 18 PSI-спостережень (`corroborating_evidence.psi_context`). Розмір росте лінійно з кількістю аномалій.

**Зробити:**
- `app/agent/context_builder.py`: `build_monitoring_context(result, max_chars) -> str`;
- порядок блоків (від обов'язкових до тих, що можна обрізати):
  1. свіжість даних (завжди першим рядком; при `stale` — явне попередження, що поточний стан невідомий);
  2. поточні значення з timestamp;
  3. recent-аномалії (найновіші першими, до 10) і стійкі серії;
  4. короткий виклад significance для recent: перевищення порогу, стійкість, якість даних, вплив `unknown`;
  5. PSI **один раз**, компактно (cpu/memory/io × some/full × avg10/avg60/avg300), з позначкою, що він не прив'язаний до аномалій у часі;
  6. зведення data issues за типами;
  7. historical — одним рядком;
  8. список того, що невідомо.
- Якщо текст перевищує ліміт, блоки 7 → 6 → 4 → 3 обрізаються з позначкою `(N items omitted)`. Блоки 1 і 8 не обрізаються ніколи.
- `AgentCore` використовує Context Builder замість `_compact_json`. Заголовок системного повідомлення — `Monitoring context` (не `Current ...`).
- `significance_evaluator.py` не змінювати; дублювання PSI усувається тільки в Context Builder.

**Тести:** розмір ≤ ліміту на 50 аномаліях; PSI зустрічається один раз; `stale` і `unknown` завжди присутні; на реальних даних текст стає коротшим у рази.

## Завдання 5. Налаштування Ollama, використання токенів і термінальний чат

**Зробити:**
- `OllamaConfig`: `num_ctx` (`JULI_OLLAMA_NUM_CTX`, 8192), `temperature` (`JULI_OLLAMA_TEMPERATURE`, 0.2), `seed` (`JULI_OLLAMA_SEED`, необов'язковий). Передавати в `options` запиту, з валідацією.
- `LLMResult`: необов'язкове поле `usage` з `prompt_eval_count`, `eval_count`, `total_duration` з відповіді Ollama. Це майбутня метрика latency і context cost для експериментів.
- `main.py`:
  - `chat` — термінальний чат з AgentCore (`/clear` очищає історію, `/context` показує останній переданий моделі контекст, `/exit`);
  - `analyze --context` — вивести те, що отримає LLM.
- Діагностика на моїй машині (тільки читання): `ollama list`, `ollama show <model>`, один тестовий запит; звіт з `prompt_eval_count` до і після Context Builder.

**Тести:** валідація конфігу; `options` присутні в тілі запиту; `usage` парситься або відсутній без помилки.

## Завдання 7. Перевірка: що працює, а що ні

Після завдань 1–6 виконай і зведи результати в таблицю **Перевірка | Очікування | Результат | Працює?**:

1. `pytest -q` повністю і `git diff --check`.
2. Чиста установка: тимчасовий каталог, `JULI_DB_PATH=...`, `main.py init-db`, `collect` 30 с, `analyze` → `fresh`.
3. Реальна база (копія): `analyze` → `stale`, 0 recent, 4 historical.
4. Свіжий збір на реальній системі 2–3 хв → `fresh`, поточні значення збігаються з `top` або `free -m` (у межах похибки).
5. **Контрольоване навантаження CPU** (тільки після мого підтвердження, наприклад `timeout 60 sh -c 'yes > /dev/null & yes > /dev/null & wait'` під кількість ядер) → recent-аномалії, стійка серія, Evidence Profiles; після завершення — повернення до норми.
6. `analyze --context`: розмір у межі ліміту, PSI один раз, свіжість першим рядком.
7. Ollama: `prompt_eval_count` до і після; чи вміщується весь промпт у `num_ctx`.
8. Сценарії `main.py chat` (зберегти відповіді моделі дослівно):
   - «Що зараз відбувається із системою?» при `stale` даних — модель має сказати, що поточний стан невідомий;
   - те саме при свіжих даних без навантаження;
   - те саме під навантаженням CPU;
   - «Яка причина високого CPU?» — модель не повинна вигадувати причину і має запропонувати read-only перевірку (наприклад, список процесів).
9. Dashboard запускається і показує дані.

Підсумок: що працює, що не працює, що варто виправити перед Memory Data Model v1.
